# 文档与文案写作

写给读者的文档与界面文案，规则如下。每条都来自一次真实的纠正，并点名它防的是哪个错误。

规则本身与语言无关；例子用中文，因为问题都出在中文上。

## 唯一标准：读者能否看清指代

**判据是「指代是否清楚」，不是「有没有代词」。**

代词与口语化表达值得避免，但指代对象在同句或上一行已经明确时，用代词**缩短了句子**，读者不花任何代价。反过来，把每个代词都换成名词，本身就是一种坏写法：它会写出「清掉这个目录……该目录不是用户内容……选 `keep` 时该目录留下」——毫无歧义，也毫无可读性。

**只有指代真的不清楚时才重复全称。**

| 情况 | 选择 | 例 |
| --- | --- | --- |
| 指代对象就在上一句、同句内唯一 | **保留代词**，更简洁 | ✅「任务会话有自己的上下文……**它**看不到队长的会话」 |
| 机械替换后句子变笨 | **保留代词** | ❌「清掉这个目录……**该目录**不是用户内容……**该目录**留下」→ ✅ 第三处改回「连同任务空间留下」 |
| 指代对象隔了半段，或有两个候选 | **重复全称** | ❌「`create` 与 `dispatch` 知道会话 id，所以**它**写进任务记录」→ ✅「所以**该 id** 被写进任务记录」 |
| 指代对象是本段主角，却不在这一句里 | **重复全称** | ❌「**它**被写成 DSH 对那个模式的全部含义」→ ✅「**`danger-full-access`** 被写成……」 |
| 主语被前一句的另一个名词抢走 | **点名主语** | ❌「（配置项）……**It** governs only the sessions opened after it.」→ ✅「**The setting** governs only……」 |

## 全称与简称

**简称必须为读者省下什么。** 判据是它缩短了多少，不是能不能缩。

- **全称本来就只有两三个字时，不要再造简称。**「源码根」缩成「源根」只省一个字，却多出一个要认的词——每次都是亏的。「会话」「分支」「仓库」同理：直接重复全称。
- **只有既已通行、又确实短得多的简称才用**（如 DSH 指 DeepSeek Harness），并在首次出现处交代一次。
- **选定一个词之后就不要再换。** 同一件事在文档里换着叫，读者得先想明白这些名字指的是一个东西。

## 对齐宿主自己的用语

**概念属于宿主产品或框架时，用那个产品自己界面上的词。** 不要另造一个平行说法；插件自己的界面文案与随包文档也必须用同一个词。

- 动笔前先找到宿主的原词：界面文案、语言文件，或产品自己的文档。**不要从 API 值反推。**
- **API 值与配置键是标识符，不是显示文案**——它们保持原样，改的是旁边的标签。

实例：DSH 的三档沙箱权限在中文界面叫「仅可查看 / 工作区内修改 / 完全权限」（`read-only` / `workspace-write` / `danger-full-access`）。某插件把第三档写成「完全访问」——既对不上界面，也对不上 API 值。改法：标签改成「完全权限」，`danger-full-access` 不动。

## 口语化：有更准的词就换

| 改为 | 原为 |
| --- | --- |
| 使用者 / 用户 | 用的人 |
| 工作 | 干活 |
| 转后台 | 丢后台 |
| 徒劳 | 白跑 |
| 保留 | 干脆留着 |

**但口语词描述的是读者能直接感知的状态、且没有更准的书面替代时，保留它。**「卡住」比「停滞」更具体——用口语的那个。

## 只写是什么、怎么用、注意事项

**写清这个东西是什么、怎么用、有哪些功能、要注意什么。不要列它「没有」什么。**

- 「这些工具只做上面这些：没有自动轮询的看门狗、没有按规则自动 steer/cancel、没有归档」——这是在列缺失。说清工具做什么就够了；一份缺失清单对读者没有用。
- **真正的注意事项要留**：「这个操作不可撤销」「`force` 从工具侧会被拒绝」。那些是注意事项，不是缺失。
- **不解释自明之事，不复述默认规则。** 手册不必写「读者只需要看这一份」——它本身就是手册。一句话说到即可，不要再用第二句去指第一句。

## 改写既有文案：先定范围

**已经写好并经确认的文案，大改之前先问。**

- 对方说「尽量不改」「稍微精简」时，**不要整段替换**。先把范围摆出来——改哪几节、各删多少行——等对方点头。把「稍微精简」理解成整段重写、把 227 行的一节压到 72 行，是发生过的，结果只能全部回退。
- **新增文案**（新文档、新界面字符串、新章节）可以直接起草初稿：先写一版再改，比来回问省事。

## 留好退路

- **整段回退优于逐处修补**：`git checkout HEAD -- <文件>`。回退是原子的；逐处修补会留下半新半旧的措辞，比两者都难发现。
- **批量替换写成脚本，不要手改。** 一行一条规则，每条要求唯一命中——规则失效时它自己报出来，而不是悄悄没生效、或者生效两次。
- **改完必须复查**，并且专门查批量替换会弄坏的东西：链接与锚点、混进锚点里的不可见字符、指向已重命名文件的路径。**自己引入的缺陷要主动报告**，不要留给读者去发现。

## 实例：一次批量替换与它的检查

把一个词在多个文件里换掉，可用的骨架：

```js
// 一行一条规则；命中 0 次或命中多次都报出来，不要照改。
// 悄悄不生效，正是改名只做了一半的原因。
const RULES = [["旧词", "新词"], ...]
for (const [from, to] of RULES) {
  const n = text.split(from).length - 1
  if (n === 0) { console.log(`MISS ${from}`); continue }
  text = text.split(from).join(to)
}
```

改完之后、报告完成之前：

1. **数一遍残留**：该清零的旧词应当为 0。
2. **查全部链接与锚点**——标题改了，锚点就跟着变；由已不存在的标题生成的锚点永远解析不到。
3. **给新加的检查做阴性对照。** 不会失败的验证不算验证：拿改动前的版本跑一遍，确认它**失败**。只断言当前文本的测试是复述，不是守卫。
4. **查编码与行尾**（如果有 shell 往返碰过文件）：合法 UTF-8、无 BOM、行尾符合仓库要求（不一致时 `git diff` 会警告）。

## 交付前自查

- [ ] 每个代词的指代都一目了然；其余写成名词。
- [ ] 没有为本来就很短的全称造简称。
- [ ] 属于宿主的概念用宿主自己的标签；标识符未动。
- [ ] 缺失清单已删；真正的注意事项保留。
- [ ] 既有文案的改写范围事先已确认。
- [ ] 链接与锚点可达；批量替换已复查并做过阴性对照。
- [ ] 文件是合法 UTF-8，行尾符合仓库要求。
